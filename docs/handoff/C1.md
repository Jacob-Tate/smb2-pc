# C1: Steam Controller diagnosis (research only)

Date: 2026-11-17. Source code untouched. "Primary" = read from SDL source/releases; "inferred" = reasoning.

## Summary

- The new (2026) Steam Controller is codenamed "Triton". SDL3 (>= 3.4.0) has a dedicated HIDAPI driver that
  talks to it directly over USB or Bluetooth LE, with no Steam client. It is on by default; no hint is needed.
- No SDL2 release supports it (latest 2.32.10; the SDL2 branch, now 2.33 dev, has no Triton code). Upgrading SDL2 does not help.
- smb2-pc cannot fix this without SDL3 (directly, or via sdl2-compat, which needs two DLLs on Windows).
- Recommendation: migrate smb2-pc to SDL3, statically linked, built from source for i686 and x86_64. About 330 `SDL_` references in 20 files, of which about 110 are in `src/input/input_sdl2.c` and about 90 in `platform_sdl2.c`. Roughly 1.5 to 2.5 days of work, split into 4 subtasks (section 5).
- Cheap interim workaround for the user: add the exe to Steam as a non-Steam game. Steam Input then presents an Xbox-style virtual pad (VID 0x28DE PID 0x11FF, "Steam Virtual Gamepad"), which SDL2 handles. This is inferred and has not been tested.

## 1. How SDL3 3.4.x supports the new Steam Controller (primary)

- Driver: `src/joystick/hidapi/SDL_hidapi_steam_triton.c` (`SDL_HIDAPI_DriverSteamTriton`).
  - https://github.com/libsdl-org/SDL/blob/release-3.4.x/src/joystick/hidapi/SDL_hidapi_steam_triton.c
  - Registered in `SDL_hidapijoystick.c` (the `SDL_JOYSTICK_HIDAPI_STEAM_TRITON` block; the file also has the `STEAM`, `STEAM_HORI` and `STEAMDECK` blocks).
  - The old-controller driver `SDL_hidapi_steam.c` is separate.
- First commit: "Added support for the new Steam Controller", 2025-11-12, 15 files, +971/-127. It adds the 532-line `SDL_hidapi_steam_triton.c`.
  - https://discourse.libsdl.org/t/sdl-added-support-for-the-new-steam-controller/64747
  - The file exists in release-3.4.0 (published 2026-01-01).
- Later fixes, all cherry-picked into the 3.4.x branch (commit list for the file, from the GitHub API):
  - 2026-01-30: updated packet handling.
  - 2026-02-12: report 0x45 is used for BLE.
  - 2026-05-01: `SDL_SendGamepadEffect()` support.
  - 2026-05-14: rumble fix; touchpads, stick capacitive touch and grip sense; BLE report-format fix.
  - 2026-05-18: touchpad finger-detection fix.
  - 2026-05-28: "Add support for new Steam Controller input report" (report 0x47 with timestamps). https://discourse.libsdl.org/t/sdl-add-support-for-new-steam-controller-input-report/68237
  - 2026-05-29: rumble moved to SDL's rumble thread.
  - 2026-11-06 and 2026-11-14: "harden against steam client disabling triton IMU".
- Release 3.4.10 was published 2026-05-31, so it contains everything up to and including the 2026-05-28/29 commits (including the 0x47 input report). The file is 711 lines in the 3.4.10 tag.
  - 3.4.20 is the newest 3.4.x release in the GitHub API listing. If the 2026-11 fixes matter, pin a newer 3.4.x than 3.4.10. Aurora pins 3.4.10 (`extern/aurora/cmake/AuroraDependencyVersions.cmake`: `AURORA_SDL3_VERSION "3.4.10"`, `AURORA_SDL3_REF "refs/tags/release-3.4.10"`).
- IDs, from `src/joystick/controller_list.h` (release-3.4.x). All are VID 0x28DE, and all map to `k_eControllerType_SteamControllerTriton`:
  - 0x1302: Steam Triton controller (USB).
  - 0x1303: Triton (BLE).
  - 0x1304: Proteus dongle.
  - 0x1305: Nereid dongle.
  - For the dongles, the driver claims HID interfaces 2 to 5 (`IsProteusDongle`, `IsSupportedDevice` in the Triton file).
  - Older controllers are unchanged: 0x1101, 0x1102, 0x1105, 0x1106, 0x1142 (dongle), 0x1201 and 0x1202 ("V2"/HEADCRAB), 0x1205 (Steam Deck). 0x11FF is the Steam virtual gamepad.
  - `usb_ids.h` lists the dongle PIDs `USB_PRODUCT_VALVE_STEAM_PROTEUS_DONGLE` 0x1304 and `USB_PRODUCT_VALVE_STEAM_NEREID_DONGLE` 0x1305.
- Hint and default: the driver's `IsEnabled()` is `SDL_GetHintBoolean(SDL_HINT_JOYSTICK_HIDAPI_STEAM, SDL_GetHintBoolean(SDL_HINT_JOYSTICK_HIDAPI, SDL_HIDAPI_DEFAULT))`.
  - `SDL_HIDAPI_DEFAULT` is `true` on every platform except Android, iOS, tvOS and visionOS (`SDL_hidapijoystick_c.h`).
  - So on Windows it is enabled by default. `SDL_HINT_JOYSTICK_HIDAPI_STEAM` ("SDL_JOYSTICK_HIDAPI_STEAM") only forces it. The hints.h text, which says the default is "0" and mentions Bluetooth, is stale for this driver. Nothing has to be set.
- Lizard mode: on init the driver sends `SETTING_LIZARD_MODE = LIZARD_MODE_OFF` (Triton file line ~142), so the pad stops emulating keyboard and mouse and reports as a gamepad. There is a watchdog that re-enables lizard mode when the app stops talking to the pad.
- What partyboard/Aurora does:
  - Aurora's `extern/aurora/lib/gamepad.cpp:455` calls `SDL_Init(SDL_INIT_HAPTIC | SDL_INIT_JOYSTICK | SDL_INIT_GAMEPAD | SDL_INIT_SENSOR)`, and line 333 calls `SDL_OpenGamepad`.
  - `extern/aurora/lib/window.cpp:430-453` sets hints, none Steam-related: ORIENTATIONS, X11 bypass compositor, screensaver name, `JOYSTICK_HIDAPI_GAMECUBE_RUMBLE_BRAKE`, touch/mouse events, and `JOYSTICK_ALLOW_BACKGROUND_EVENTS` (the last conditionally, plus `set_background_input`).
  - A grep of `src/` and `extern/aurora/lib` found no `SDL_HINT_JOYSTICK_HIDAPI_STEAM` and no `SDL_JOYSTICK_HIDAPI` set anywhere. `src/port/button_icons.cpp` only maps the Steam Deck icon family.
  - Conclusion: it works in partyboard purely because SDL3 3.4.10 ships the driver and enables it by default.
- Aurora's SDL3 linkage: `AuroraSDL3Provider.cmake` prefers `SDL3::SDL3-static` where available (`AURORA_SDL3_LINKAGE`, `_default_linkage`).

## 2. Does any SDL2 release support it? NO (primary)

- Latest SDL2 release is 2.32.10 (tag `release-2.32.10`, published 1 Sep; release notes mention only audio, macOS dock and Switch Pro fixes: https://github.com/libsdl-org/SDL/releases/tag/release-2.32.10).
- The SDL2 branch (`SDL_version.h`: 2.33 dev) lists `src/joystick/hidapi/`: `SDL_hidapi_steam.c` and `SDL_hidapi_steamdeck.c` plus `steam/`. There is no `SDL_hidapi_steam_triton.c` and no `SDL_hidapi_steam_hori.c`.
  - https://github.com/libsdl-org/SDL/tree/SDL2/src/joystick/hidapi
  - `controller_list.h` on the SDL2 branch and at 2.32.10 ends the Valve entries at 0x1205. There are no 0x1302 to 0x1305 entries.
  - `grep -ci triton` on 2.32.10's `SDL_hidapi_steam.c` gives 0.
  - The old `SDL_hidapi_steam.c` driver is gated by `SDL_IsJoystickSteamController(vid, pid)`, which only knows the 0x11xx/0x12xx PIDs, and is off by default (`SDL_GetHintBoolean(SDL_HINT_JOYSTICK_HIDAPI_STEAM, SDL_FALSE)`).
- SDL2 is in maintenance mode, and the Triton work landed only on the main/3.4.x branches. Upgrading smb2-pc from 2.30.9 to 2.32.10 will not help. Only sdl2-compat (which is SDL3 underneath) offers a "SDL2 API" path.

## 3. What SDL2 2.30.9 most likely sees without Steam (inferred)

Not testable from here. Reasoning:

- 2.30.9 has no driver that claims PIDs 0x1302 to 0x1305. The old Steam driver is disabled by default and does not know these PIDs anyway.
- The HIDAPI driver list does not claim the device. The Windows joystick backends (WGI / DirectInput / XInput) enumerate HID game controllers or XInput devices.
- The controller's USB descriptor, without Steam, is "lizard mode": keyboard and mouse HID interfaces (the same behaviour as the older Steam controllers) plus the vendor-defined interface that SDL3 uses. I did not find the descriptor in a primary source.
- Most likely result:
  - Nothing appears as a joystick.
  - The pad acts as keyboard and mouse. The game reads the keyboard through `SDL_GetKeyboardState`, and the keyboard fallback is on (`s_keyboard_fallback`), so some buttons may seem to do things. The mouse is ignored.
  - There is a small chance a generic HID joystick node appears (the port's raw-joystick fallback at `input_sdl2.c:165-173` would then print "no controller mapping for GUID ..."). The diagnostic flag in section 6 settles which case it is.

## 4. Options for smb2-pc

### 4a. Upgrade SDL2: not viable (section 2). Effort 0, value 0.

### 4b. sdl2-compat (SDL2 API implemented over SDL3)

- Builds `SDL2.dll` that loads `SDL3.dll` at run time.
- Static build is only for Linux/QNX. `CMakeLists.txt` of sdl2-compat:
  - line 88: `option(SDL2COMPAT_STATIC "Enable building static SDL2 link library" OFF)`
  - line 96-97: `if(SDL2COMPAT_STATIC AND NOT (CMAKE_SYSTEM_NAME MATCHES "Linux|QNX")) message(FATAL_ERROR "Static builds are only supported on Linux or QNX.")`
  - https://github.com/libsdl-org/sdl2-compat/blob/main/CMakeLists.txt
- So on MinGW this means shipping `SDL2.dll` + `SDL3.dll` beside the exe (for both i686 and x86_64). That breaks the "no SDL DLL" property.
  - Also, the exe would be linked against the import lib of `SDL2.dll`, not the static `libSDL2.a`; the SDL2 static link in `CMakeLists.txt:438-445` would have to change.
- Pros: zero source changes, about half a day to try. Cons: two DLLs, a DLL search-path or side-loading risk, and an extra layer (sdl2-compat 2.32.7x is a young project).
  - The virtual joystick API, `SDL_GetWindowWMInfo` and the display mode APIs are all emulated; they are the likeliest to differ.
- Useful as a 1-hour experiment to prove the hardware works (drop sdl2-compat's `SDL2.dll` and the official `SDL3.dll` from the mingw SDL3 package beside the exe; `--list-controllers` should then show the pad). Not recommended as the shipping solution.

Known SDL2 to SDL3 mappings (SDL's `docs/README-migration.md` is the primary reference; SDL3 also ships `build-scripts/SDL_migration.cocci` and `build-scripts/rename_symbols`):

- Headers: `#include <SDL.h>` to `<SDL3/SDL.h>`; `SDL_opengl.h` to `<SDL3/SDL_opengl.h>`.
- Init: `SDL_INIT_GAMECONTROLLER` to `SDL_INIT_GAMEPAD`; `SDL_Init`, `SDL_InitSubSystem`, `SDL_WasInit` and `SDL_GetHint` now return/accept bool or flags (`< 0` checks must flip: success is `true`).
- Events: `SDL_QUIT` to `SDL_EVENT_QUIT`; `SDL_KEYDOWN` to `SDL_EVENT_KEY_DOWN`; `SDL_WINDOWEVENT` with sub-events becomes separate `SDL_EVENT_WINDOW_*` types; `SDL_CONTROLLERDEVICEADDED` to `SDL_EVENT_GAMEPAD_ADDED`; `SDL_JOYDEVICEADDED` to `SDL_EVENT_JOYSTICK_ADDED`. `event.cdevice.which` is now an instance ID, not a device index, so the hot-plug flow changes (`input_on_device_added(int index)` becomes ID based).
- Gamepad/joystick (tricky, see below).
- Keyboard: `SDL_GetKeyboardState` returns `const bool*`; the `SDL_SCANCODE_*` names are unchanged.
- Windows/GL:
  - `SDL_CreateWindow(title, x, y, w, h, flags)` becomes `SDL_CreateWindow(title, w, h, flags)`, with centring handled by the window properties.
  - `SDL_WINDOW_FULLSCREEN_DESKTOP` is gone: fullscreen is `SDL_SetWindowFullscreen(win, bool)`; borderless-vs-exclusive depends on `SDL_SetWindowFullscreenMode` (NULL means borderless desktop).
  - `SDL_WINDOW_ALLOW_HIGHDPI` becomes `SDL_WINDOW_HIGH_PIXEL_DENSITY`; `SDL_GL_GetDrawableSize` becomes `SDL_GetWindowSizeInPixels`.
  - Display indices become `SDL_DisplayID`: `SDL_GetNumVideoDisplays` to `SDL_GetDisplays`, `SDL_GetNumDisplayModes`/`SDL_GetDisplayMode` to `SDL_GetFullscreenDisplayModes`, `SDL_GetClosestDisplayMode` to `SDL_GetClosestFullscreenDisplayMode`, `SDL_GetDisplayDPI` to `SDL_GetDisplayContentScale`, `SDL_GetWindowDisplayIndex` to `SDL_GetDisplayForWindow`.
  - `SDL_GL_*` attribute and context functions keep their names but return bool; `SDL_GL_GetProcAddress` returns `SDL_FunctionPointer`.
  - `SDL_GetWindowWMInfo`/`SDL_SysWMinfo` is replaced by `SDL_GetPointerProperty(SDL_GetWindowProperties(w), SDL_PROP_WINDOW_WIN32_HWND_POINTER, NULL)` (render_d3d12.c, pc_file_dialog.c, platform_sdl2.c).
  - `SDL_CreateRGBSurfaceWithFormatFrom` to `SDL_CreateSurfaceFrom`; `SDL_FreeSurface` to `SDL_DestroySurface`; `SDL_PIXELFORMAT_RGBA32` stays.
- Threads/semaphores: `SDL_CreateThread` is the same shape; `SDL_sem` becomes `SDL_Semaphore`, `SDL_SemPost` to `SDL_SignalSemaphore`, `SDL_SemWaitTimeout` to `SDL_WaitSemaphoreTimeout` (bool). Note `audio_miniaudio.c` already uses miniaudio for output, so SDL audio is not used (it still passes `SDL_INIT_AUDIO`).
- Paths: `SDL_GetBasePath` returns `const char*` that must NOT be freed in SDL3 (`assets.c:281-285` does `SDL_free(base)`, which would be a bug after migration); `SDL_GetPrefPath` still returns an `SDL_free`-able string.
  - Check that the pref path resolves to the same directory so existing saves still load (same org/app on Windows gives `%APPDATA%\org\app\`).
- Main: `SDL_MAIN_HANDLED` is still honoured. The `main=SDL_main` define in `CMakeLists.txt:475` and `libSDL2main.a` are not needed. SDL3 has no separate main library for Windows (entry code comes from `<SDL3/SDL_main.h>` and `SDL_RunApp` in the main lib). With `SDL_MAIN_HANDLED`, remove the define and link only `SDL3`. Inferred.
- Hint: `SDL_HINT_WINDOWS_DPI_AWARENESS` is removed in SDL3. SDL3 windows are per-monitor DPI aware by default, so the `main.c:97` and `platform_sdl2.c:109` calls are deleted. Check that the default-window sizing in `pc_settings.c` still matches (`SDL_GetDisplayUsableBounds` plus content scale).

Tricky parts:

1. Gamepad API (`input_sdl2.c`). SDL3 is ID-based, not index-based: `SDL_NumJoysticks()` + index to `SDL_GetGamepads(&n)` returning `SDL_JoystickID*` (must be `SDL_free`'d); `SDL_IsGameController(i)` to `SDL_IsGamepad(id)`; `SDL_GameControllerOpen` to `SDL_OpenGamepad(id)`; `SDL_GameControllerGetAxis` to `SDL_GetGamepadAxis`; `SDL_CONTROLLER_BUTTON_*` to `SDL_GAMEPAD_BUTTON_*` (note the rename: `A/B/X/Y` become `SOUTH/EAST/WEST/NORTH`, and `LEFTSHOULDER` to `LEFT_SHOULDER`); `SDL_GameControllerType` to `SDL_GamepadType`. `input.h` and `button_prompts.h` expose `SDL_GameControllerButton`/`SDL_GameControllerType` in public headers, so the type changes ripple into the game shims (`src/game/shim/button_prompts.c`).
2. `SDL_HINT_GAMECONTROLLER_USE_BUTTON_LABELS` (input_sdl2.c:214) is gone. In SDL3 the Nintendo "label vs position" choice is made by `SDL_GetGamepadButtonLabel` / `SDL_HINT_GAMECONTROLLER_...` handling in the mapping, so the port's "Nintendo pads map by label" behaviour must be re-verified on a Switch Pro pad (virtual Switch pad VID 0x057E PID 0x2009 test hook helps).
3. Virtual joystick test hooks (`input_sdl2.c:615-690`). The API exists in SDL3: `SDL_AttachVirtualJoystick(const SDL_VirtualJoystickDesc*)` returns an instance ID directly (no index to ID lookup needed, so `vpad_detach` simplifies); `SDL_SetJoystickVirtualAxis/Button`, `SDL_DetachVirtualJoystick(id)`; `desc.type = SDL_JOYSTICK_TYPE_GAMEPAD`; `desc.naxes = SDL_GAMEPAD_AXIS_COUNT`, `nbuttons = SDL_GAMEPAD_BUTTON_COUNT`. `SDL_VIRTUAL_JOYSTICK_DESC_VERSION` is still required. The scripted axis scaling (trigger `lt*2-32768`) and the `SDL_HINT_JOYSTICK_ALLOW_BACKGROUND_EVENTS` hint must be re-checked in the headless test harness (P0.4), because the virtual-device mapping and the button numbering follow the SDL3 gamepad enum (button bit i of the script maps to `SDL_GAMEPAD_BUTTON_i`, whose enum values differ from SDL2's for some entries, e.g. SDL3 has `MISC1`, paddles, and the touchpad in different positions: verify `(buttons >> b) & 1`).
4. Mappings: `SDL_GameControllerAddMappingsFromFile("gamecontrollerdb.txt")` to `SDL_AddGamepadMappingsFromFile`. Format is mostly compatible, but SDL3 uses a new GUID layout/CRC, so an SDL2-era `gamecontrollerdb.txt` may partly not match; the README says the exe adds mappings for unknown controllers (README line ~94), which should be re-tested.
5. Display modes and fullscreen (`pc_settings.c`, `platform_sdl2.c`) are the most invasive non-input piece: the whole fullscreen/borderless/exclusive switching and the resolution list rely on SDL2 semantics (`SDL_WINDOW_FULLSCREEN_DESKTOP` and `SDL_SetWindowDisplayMode`).
6. Event handling: the `which` field meaning changes (index to instance ID) and ADDED/REMOVED are single events per device; the dedupe comment in `platform_sdl2.c:181-185` (a mapped controller sends both JOY and CONTROLLER events) no longer applies; SDL3 sends `SDL_EVENT_JOYSTICK_ADDED` and `SDL_EVENT_GAMEPAD_ADDED` both, so keep the dedupe, or use only the gamepad event plus `SDL_IsGamepad()`-negative joystick events for the raw fallback.
7. File dialog (`pc_file_dialog.c`): SDL is only used for the HWND, `SDL_MinimizeWindow`/`RestoreWindow`/`RaiseWindow` and `SDL_GetWindowFlags` (`SDL_WINDOW_FULLSCREEN`, `SDL_WINDOW_FULLSCREEN_DESKTOP`). The dialog itself is Win32 (comdlg32), so it is a mechanical change (SDL3 also has `SDL_ShowOpenFileDialog`, but there is no need to use it). `SDL_GetWindowFlags` now returns `SDL_WindowFlags` (64-bit) and has only `SDL_WINDOW_FULLSCREEN`.
8. D3D12 glue (`render_d3d12.c`): only the HWND lookup and `SDL_GetWindowSizeInPixels`. Easy. The renderer is created with `SDL_WINDOW_OPENGL` or not? The window flags in `platform_sdl2.c` are `SDL_WINDOW_OPENGL | RESIZABLE | ALLOW_HIGHDPI`; check that the D3D12 path with an OpenGL-flagged window still behaves the same under SDL3 (SDL3 creates the GL context lazily, but the flag still triggers pixel-format setup).
9. SDL's libm copy in `src/detmath/fdlibm`: no change. The files are copied from SDL 2.30.9 `src/libm` as a source snapshot (docs/detmath.md line 44), independent of the linked SDL version. They use their own `math_libm.h`, `math_private.h` and a stub `SDL_assert.h` (a no-op macro). Game code references only the `pc_*` renamed symbols; SDL3 linking does not touch them. SDL3's own libm (`SDL_libm`) is not used by the game. The only note: docs/detmath.md line 62 says the exes "still import libm for SDL, miniaudio and the renderers"; this stays true. Re-run the detmath checks (`llvm-nm -u` shows only `pc_*`) after the migration as a sanity check, but expect no change in results.
10. Determinism: input is read at the top of each frame (polled once per frame by `input_poll_gc_pads`); the migration must not change timing (`SDL_GetPerformanceCounter` and `SDL_Delay` have the same semantics in SDL3; `SDL_Delay` is unchanged).

Getting SDL3 3.4.10 static libs for MinGW (i686 and x86_64):

- The official `SDL3-devel-3.4.10-mingw.tar.gz` (verified by downloading and listing it: https://github.com/libsdl-org/SDL/releases/download/release-3.4.10/SDL3-devel-3.4.10-mingw.tar.gz) contains, for both `i686-w64-mingw32/` and `x86_64-w64-mingw32/`: `lib/libSDL3.dll.a` (import lib), `lib/libSDL3_test.a`, `bin/SDL3.dll`, CMake config files (`SDL3sharedTargets`, `SDL3testTargets`, `SDL3headersTargets`), `lib/pkgconfig/sdl3.pc`, `include/SDL3/*`, and a licence. It is shared only: there is no `libSDL3.a`. So it cannot give a static link (SDL2's own package was the same, which is why README builds 32-bit SDL2 by hand with `--disable-shared --enable-static`).
- Therefore build static from source (the official source tarball `SDL3-3.4.10.tar.gz` exists on the release page; the tag is `release-3.4.10`, ref commit `8e37db5e797b6167f3a00d697d816a684bd259c7`):
  - i686 (uses `cmake/mingw32.cmake`, the gcc toolchain that matches the game build) and x86_64 (uses `cmake/mingw64.cmake` or `cmake/llvm-mingw64.cmake` to match whichever toolchain links the x64 exe).
  - Configure (indicative, not run): `cmake -S SDL3-3.4.10 -B build32 -DCMAKE_TOOLCHAIN_FILE=<smb2-pc>/cmake/mingw32.cmake -DSDL_SHARED=OFF -DSDL_STATIC=ON -DSDL_TEST_LIBRARY=OFF -DSDL_TESTS=OFF -DSDL_INSTALL_TESTS=OFF -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=<mingw_deps>/i686-w64-mingw32` then `cmake --build build32 && cmake --install build32`. Same for 64-bit. The result is `lib/libSDL3.a`, `include/SDL3/`, and `lib/cmake/SDL3/`.
  - Link line: `libSDL3.a` plus the Windows system libs the existing line already has (`gdi32 user32 winmm imm32 ole32 oleaut32 version uuid advapi32 setupapi shell32`) and, new for SDL3, `cfgmgr32` (HIDAPI device enumeration), `ws2_32`/`rpcrt4` as needed. The final list is easiest to read from the generated `sdl3.pc` `Libs.private`. Keep `-static -static-libgcc` from the toolchain files.
  - `dinput8` and `winhttp` in the current list are not SDL3 requirements (winhttp is for the updater).
  - The cmake toolchain files set `CMAKE_FIND_ROOT_PATH` to `/usr/<triplet>`; for the SDL3 install prefix, add it to `CMAKE_FIND_ROOT_PATH` or use the existing `MINGW_DEPS_DIR` handling in `CMakeLists.txt:83-110` (swap `SDL2`/`SDL.h` for `SDL3`/`SDL3/SDL.h`).
- Risk: needs a one-off check that the HIDAPI Windows backend initialises correctly in a fully static MinGW build (SDL's own static builds do this; partyboard uses a static SDL3 per Aurora's `SDL3::SDL3-static` preference). The whole static SDL3 adds roughly 2 to 3 MB per exe (inferred from SDL2's static size; not measured).
- Effort and risk of 4c: 1.5 to 2.5 days of agent time; risk medium (input behaviour parity: button labels, virtual-pad tests; fullscreen/display handling on the three window modes; build toolchain on i686). Benefit: also fixes any future controller, and matches partyboard.

## 5. Recommendation and proposed C2 split

Do c: migrate to SDL3, statically linked. Do the quick `--list-controllers` flag first (C2a), as it works on SDL2 today and tells us whether anything is visible. Keep the SDL2 path buildable until SDL3 is proven, using a thin compatibility header, so C2c can be bisected.

## 6. `--list-controllers` diagnostic spec

Behaviour: `smb2_pc_port.exe --list-controllers` initialises only `SDL_INIT_JOYSTICK | SDL_INIT_GAMECONTROLLER` (no window), prints the list below to stdout (also copies it to `controllers.txt` beside the exe so the user can paste it), then waits about 1.5 s pumping `SDL_PumpEvents` so Windows enumeration finishes, and exits 0.

Print:

1. SDL version: compile-time (`SDL_VERSION`) and run-time (`SDL_GetVersion`, plus `SDL_GetRevision`); and platform.
2. Relevant hints with their effective values: `SDL_JOYSTICK_HIDAPI`, `SDL_JOYSTICK_HIDAPI_STEAM`, `SDL_JOYSTICK_ALLOW_BACKGROUND_EVENTS`, `SDL_HINT_GAMECONTROLLER_USE_BUTTON_LABELS`, `SDL_JOYSTICK_RAWINPUT`, `SDL_JOYSTICK_WGI`, `SDL_XINPUT_ENABLED`.
3. `SDL_NumJoysticks()` count. For each joystick index: instance ID, name (`SDL_JoystickNameForIndex`), VID and PID in `0x%04X` form (`SDL_JoystickGetDeviceVendor/Product`, plus product version), GUID string, type (`SDL_JoystickGetDeviceType`), `SDL_IsGameController` yes/no, the mapping string (`SDL_GameControllerMappingForIndex`, or "none"), controller type name, number of axes/buttons/hats, and the device path where available.
4. A clear verdict line:
   - `0 devices`: "SDL sees no joystick or controller devices. A controller that only does keyboard/mouse emulation is not listed."
   - Any device with VID 0x28DE: "Valve device found: VID/PID ..., this SDL version has/doesn't have a driver (SDL2 2.30.9: no driver for 0x1302 to 0x1305)".
5. HID-level listing, independent of SDL's joystick layer. Under SDL2, `SDL_hid_enumerate` is exported as `SDL_hid_enumerate` in 2.30.x; if not usable, use the Win32 SetupAPI HID list (`setupapi` is already linked): every HID interface with VID 0x28DE, printing path, usage page/usage and interface number. This shows whether Windows exposes the pad as a keyboard (page 1, usage 6), mouse (page 1, usage 2), joystick/gamepad (page 1, usage 4/5), or a vendor page (0xFF00 or similar). It answers "keyboard+mouse lizard mode vs. nothing vs. raw joystick" definitively.
6. Optionally, `--list-controllers --watch`: loop for 30 s printing `SDL_JOYDEVICEADDED/REMOVED` events (and button/axis changes of any open raw joystick), so the user can plug the pad in during the run.

What the user should send back: the full output, once with the controller plugged in over USB and Steam closed, and once with Steam running. Expected on SDL2 2.30.9 per section 3: no entries for VID 0x28DE, with HID listing showing keyboard and mouse interfaces and a vendor-defined interface. After the SDL3 migration: one entry named like a Steam Controller, with VID 0x28DE and PID 0x1302 (USB) or 0x1303 (BLE), `is gamepad = yes`.
