# X2: attract/title pixel noise (render-only or hash gap?)

## Verdict
Render-only noise from the OpenGL persistent vertex ring; not a sim value. Netplay is not affected.

## Evidence
1. Instrumented build (patch: wt/X2_tmp/x2_instr.patch) hashed everything gx_core hands to the GL backend per frame:
   vertex data (+ UV rects), `GxDrawConsts` (proj/mv/texmtx/modes/tev/fog), `GxTevConsts`, and every
   `tex_create`/`tex_image` upload. Two `--det-session --fps 60 --renderer gl` runs: all 812 frame lines identical.
   Same draws, same constants, same texels, yet frames 700-725 differ in pixels (11-16 of 26 frames per pair).
   So the sim and everything upstream of the GPU backend is identical; the difference arises inside the backend/GPU.
2. Not the async EFB copy: `SMB2_COPY_CPU_RESAMPLE=1` and `=3` still differ (14 and 16 of 26).
3. `SMB2_NO_PERSISTENT_VBO=1` (glBufferSubData instead of the persistent-mapped ring): 0 of 26 frames differ
   (frames 700-725, two runs).
4. Ring kept but `glFinish()` after every draw: 1 of 26 differs (down from ~11-16). Strongly suggests a CPU-write/GPU-read
   race (or stale-data read) in the ring in `render_opengl.c` (ring_alloc/ring_write/ring_write_rect; 4 quarters, fence on
   quarter change). I did not find the exact bug by inspection: fences look right on paper; candidates are
   attribute 7 (`a_uvrect`, rect_vbo) being read for draws that did not write rects (stale data from previous lap), and
   the coherent-mapping write timing. Not proven.
5. Not attract-only: gameplay frames 4150-4175 of the race script (ring mode) differ in 21 of 26 frames. (The no-ring
   gameplay comparison was started but runs extremely slowly without the ring; not completed.)
6. D3D12 shows the same symptom (E4 note); it has a separate upload ring (`ring_alloc` in render_d3d12.c), so a
   similar race there is plausible, but I did not test D3D12 internals.
7. Curated sim hash is unaffected (matches at polls 720/780 in all runs, per E4); no hash coverage gap found: sim state
   cannot influence pixels if the draw inputs are bit-identical.

## Netplay impact
None for sync: checksums cover sim only and render inputs are provably identical. Visible effect is up to 1/255 (GL)
sparkle on some frames. It also means pixel-exact frame comparisons are unreliable with the ring on; use
`SMB2_NO_PERSISTENT_VBO=1` (or X2 hashing) when diffing frames.

## Proposed fix
Find and fix the ring hazard in render_opengl.c (candidates in item 4), or as a fallback disable the persistent ring
(costs speed: no-ring runs were much slower in gameplay). Check the D3D12 ring the same way. Low priority.

## Not done

wt/X2_tmp) may still be running; they are slow.
