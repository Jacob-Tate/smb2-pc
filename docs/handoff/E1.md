# E1: Determinism audit (read-only, static analysis only)

Status: DONE (static). Nothing was built or run; every "runtime test" below is still open.
Paths: `pc/` = `smb2-pc/`, `dc/` = `smb2-decomp/`. Line numbers are from the tree as of 2026-11-17.

## 1. Summary

- Verdict: lockstep input relay is feasible. The simulation is single-threaded, runs exactly one tick per
  game-loop iteration (no catch-up, no skipping), DVD/ARAM/CARD are synchronous, audio is game-time driven,
  and `rand/sin/qsort/atof` are already pinned by detmath. **The renderer, fps, HFR and resolution never feed
  back into game state** (GXPeekZ is a stub, viewport/projection read-back are game-set values).
- The drift sources that exist today are all *environmental*: wall clock (`srand(OSGetTime())`, boat RNG seeded
  from `OSGetTick`), the local memory card (unlocks, options, stick gates, wide mode, timestamps), local PC
  settings reachable through game menus (language, button style, Options>Game Screen rows), and local-only
  modal UI (F1 overlay, Esc quit box, update notes, memcard notices).
- Top risks: (1) clock-seeded RNGs (D1, D2); (2) card contents and the card/option state machine (D4, D5, D8);
  (3) PC menu rows / quit box that read local state from replicated menu input (D10, D11); (4) pad hook must
  NOT be `input_poll_gc_pads` as a whole (it is also called from modal screens, and it keeps state in
  `status[0]`); (5) 8 s hang watchdog kills a client blocked in lockstep (D14); (6) cross-arch: arena and
  `.data/.bss` cannot be hashed x64 vs i686 (struct sizes differ), so the checksum must be curated field-wise (D15).
- Recommended hook: after the local sample inside `input_poll_gc_pads` (`pc/src/input/input_sdl2.c`, between the
  script-injection block ending ~L944 and the "Derive the pressed/released/repeat slots" loop at L945), enabled
  only when called from `video_finish_frame` (`pc/src/game/shim/video_shim.c:337`), with the local sample taken into
  a private buffer. Details in section 5.
- Checksum: curated field-wise hash (a few KB, microseconds) every 60 ticks plus a per-tick ring for bisecting;
  optional same-arch rolling arena hash (1/60 of 24 MiB per tick, ~40 us).
- Not decompiled / not linked, so not playable online at all: Billiards, Shot (shooting), Fight (mini_fight2),
  Soccer (futsal), Tennis. Linked: Race, Target (pilot2), Bowling, Boat, Dogfight, Baseball, Golf + main game.

## 3. Detailed answers, checklist items 1-11

### 1. Time sources
- `OSGetTime` (`os_shim.c:428-432`): `time(NULL)` wall clock in GC ticks. Game callers: `srand(OSGetTime())` at boot
  (`main_loop.c:252`) = **D1**; save/replay timestamps (`memcard_mkb2.c:234,337` display only).
- `OSGetTick` (`os_shim.c:434-437`): host QPC. Sim-relevant callers: boat seed (`boat_0.c:241,300`) = **D2**;
  `render.c:55` GPU time -> `rend_efc.c:618` = **D3**. Pure profiling callers (harmless but write wall times into
  game memory): `perf.c:88,94`, `boat_1.c`, `boat_2.c`, `pilot2_stage.c`, `dogfight_7.c:213-218` (timer_start/stop
  profile only; checked `lbl_17_bss_12B30`), `boat_0.c:336,750-762` (`lbl_14_bss_30` -> `BOAT_TICKS` stats).
- `OSTicksToCalendarTime` (`os_shim.c:443`): display of save times (`option_menu.c:800`, replay names
  `memcard_mkb2.c:280`); gmtime, no sim effect.
- Card timestamps: `card_time_now()` (`card_shim.c:421-432`) localtime; goes into `.meta` and `CARDStat.time`.
  Not sim, but differs between peers if hashed. In-memory session card uses a fixed value.
- Other RNGs: MSL `rand` (global, pinned: `pc_libc.c:17-27`, seed set only at `main_loop.c:252` and temporarily at
  `background.c:935-939` using `world_theme.unkA0 = frame_counter + rand()`, so `frame_counter` (main loop
  iterations since boot, `main_loop.c:171,251`) must match: it does if the sequence of loop iterations matches).
  Boat LCG (D2). No other `srand`/own-seed found in `dc/src` (grep `srand|OSGetTick|OSGetTime`). `pc/src` game/shim/
  render/input contain no `rand`, `time`, `clock` use that feeds the game (grep'd).
- Fix: det-mode clock (D1/D2). Proposed shim API: `pc_det_session_active()`, `g_pc_sim_frame`, session epoch.
  Runtime test T1.

### 2. Disc reads
- All synchronous. `DVDReadAsyncPrio` reads immediately and calls the callback inline (`dvd_shim.c:126-155`).
  `DVDGetCommandBlockStatus` always 0 (`dvd_shim.c:~172`). `read_entire_file_using_dvdread_prio_async` returns after
  the read (`dvd_shim.c:~262`). ARAM/ARQ: memcpy + immediate callback (`ar_shim.c:5-9,48-66`).
- Only exception: three sound read callbacks (`g_some_dvd_read_async_sound_callback{,2}`, `fn_1_33DC0`) are queued and
  run in `musyx_frame` at the end of each tick (`dvd_shim.c:99-170`, `musyx_shim.c:1153-1157`): game-time, not
  completion-time dependent. Deterministic. Queue overflow (64) falls back to inline.
- Host variance: read errors or a different disc image. Handled by D17 (manifest hash). Missing: nothing else.

### 3. Frame pacing (most important)
- One game-loop iteration = one sim tick = exactly one `video_finish_frame` call: loop at
  `dc/src/main_loop/main_loop.c:260-312` (`process_inputs` at L269, `video_finish_frame` via
  `g_something_with_video_this_also_finishes_a_frame` at L311; defined `render.c:59-71`). Baseball runs its own
  loop (`baseball_0b.c:36-75`), also one per iteration, plus 2 trailing calls with no tick (D18).
- `video_finish_frame` (`video_shim.c:239-411`) order: `musyx_frame` (L279) -> telemetry -> **`input_poll_gc_pads()`
  (L337)** -> SDL events (L338) -> modal screens (L348-377) -> present if not yet running (L380-384) -> pacer
  (L386-410).
- Pacer: `next_ns += 16666667`; if the frame was late it just does not sleep; if > 100 ms behind it resets
  `next_ns = now` (L403-409). **No catch-up ticks, no skipped ticks**: the sim simply runs slower. So the sim tick
  count is independent of wall time, render fps, vsync, MSAA, renderer.
- HFR (`video_shim.c:116-237`, `gx_hfr.c`): runs after the tick inside the pacing block, replays recorded GX
  commands at alpha; never calls game code. Reads only `main_mode` (L268). Only coupling: its present waits can
  delay the pacer sleep (not the sim). `hfr_adapt` adapts render cost only. Not a sim source.
- Renderer read-back into the game: `GXGetViewportv`/`GXGetProjectionv` return the game-set values
  (`gx_core.c:1180-1186,1799-1830`), not window sizes; `GXPeekZ` is a stub returning without writing
  (`stubs_gen.c:14`), so ZQuery results (`zquery.c`) are constant. (If anyone implements GXPeekZ for real, it must
  stay stubbed in det sessions: lens flares would then depend on GPU/resolution/MSAA.)
- The one wall-clock leak into the game is D3 (fixed by det tick).
- Lockstep implication: gating by "bundle for poll N has arrived" is sufficient; the pacer sleep is then
  redundant. Keep the sleep (so a fast LAN does not run > 60 Hz) but never use it to decide ticks.
- Runtime test T2: run the same input script with `--fps 60`, `--fps 240`, `--fps uncapped`, vsync on/off, GL vs D3D12,
  two window sizes; curated hash at tick 3600 must be identical.

### 4. Audio
- Game-visible synth runs on the game thread in 5 ms game-time ticks, 10 per 3 video frames, from `musyx_frame`
  (`musyx_shim.c:1153-1170`); voice/stream positions are advanced by the synth itself (`posFix`, lines 332,355), never
  read back from the DSP. The DSP worker (`audio_miniaudio.c`, interface `include/audio_dsp.h`) only consumes
  commands; the game thread never waits and a full queue just drops commands. There is no worker-to-game data flow
  (the only calls into `adsp_*` return void). Device, `--audio-null`, volume and underruns cannot change game state.
- Stream callbacks every 4th tick (50 Hz) are the music clock for `smgr.c` (`docs/audio.md`): deterministic.
- Residual: the synth state is shim-side state (D20). Fresh process per session. Test T3: same script with the real
  device vs `--audio-null`; hash must match.

### 5. Memory card (contents, unlocks, party games, in-memory all-unlocked card)
What the card/save contains that changes gameplay (`dc/src/main_loop/memcard_mkb2.c:30-52`, save buffer
`storymode_save_files[0xFA0]`):
- `unlock_info` (struct `UnlockInfo`, `unlock.c:13-27`, saved at +0x274): `playPoints`, `partyGames` bitmask,
  `monkeyCount` (character select, `sel.c:193`), `movies`, `masterUnlocked`, `staffCreditsGame`.
- Story/CM unlock entries (`g_load_storymode_unlock_entries`, `g_load_cm_unlock_entries`), option block
  (`fn_1_1273C`, `fn_1_16C384`, `fn_1_13FD84`), rankings (affect whether name entry appears after a game), `wideMode`
  (+0x319), `splitscreenMode` (+0x318), sound mode (+0x31A), stick gates (+0x31C, D5).
- Save timing: auto-saves are game state-machine jobs (`g_some_replay_func4`, `memcard.c:510-590`) that run to
  completion in a few ticks with the synchronous card; dialogs and error boxes wait for button presses. Identical
  card on every peer => identical frame sequence. A *different* card (missing, corrupt, other free blocks) changes
  the branch taken at the title (`adv.c:1676-1800`) and the heap allocation sequence (each job allocs 0xC0 + file
  size from `currentHeap`).
How party games are unlocked: `unlock_party_game(id)` spends 2500 play points and sets `partyGames |= 1<<id`
(`unlock.c:~503-507`), prompted in sel_ngc (`sel_ngc.c:1121,2001`). The 6 locked ones are bits 9, 0xA, 0xC, 0xD,
0xF, 0x10 (`sel_ngc.c:1900-1915`); `get_num_of_unlocked_party_games` = min(12, 6 + count of set bits)
(`unlock.c:585-592`). So `partyGames = 0x1B600` makes `are_all_party_games_unlocked()` true. (There is also a debug
override `DIP_DEBUG && DIP_PLAY_STG_ALL`; do not use it: it changes other behaviour.)
How to give a session an all-unlocked in-memory card (proposal, E2):
1. `card_shim.c`: session mode = file operations go to RAM, slot A mounted, file table empty at start, fixed
   timestamps, never written to disk, `pc_gci_startup` import and `pc_memcard_ui` disabled.
2. At boot, right after `clear_unlock_info()` (`main_loop.c:~245`): `unlock_info.partyGames = 0x1B600;`
   `monkeyCount`/movies/stage unlocks = canonical constants chosen by the host (identical on all peers),
   `modeCtrl.wideMode=0`, `splitscreenMode` canonical, gates default, `locale` forced. Because the card starts empty,
   the title's PC branch (`adv.c:1747-1754`, case 4 -> 6) makes the game create its own file through its normal
   save code (`g_save_game_data`, which reads `unlock_info`), so no hand-built checksummed image is needed. After
   that the game loads/saves normally against the RAM card. Alternative if a pre-seeded card is preferred: run the
   game's save routine once at boot into the RAM card.
3. Open question: which Challenge/Practice stage unlocks (`g_load_cm_unlock_entries`) matter for Competition stage
   lists; inspect `course.c` and test T7 (list stages offered in Competition with the default vs. fully unlocked card).
Runtime test T4: boot twice with two different on-disk cards under `--det-session`; curated hash at tick 600 equal.

### 6. PC settings and env vars that change the simulation
Affect the sim (must be forced or equal on all peers): language/`locale` (D7), `wideMode`/`splitscreenMode` (D8),
button style (D9), Options>Game Screen PC rows (D10), Esc/update/notice (D11), controller calibration and gates (D5),
env/CLI hooks (D13), `SMB2_HEAP_CHECK` (D13).
Render/local only (do not affect sim): display mode, resolution, vsync, MSAA, fps/HFR, renderer, aspect (`pc_settings_output_aspect`
only affects the output box), master volume, update_check. `gc_stick.c` and keyboard mapping run on local input
before it goes on the wire: fine, provided the wire carries post-processed values (D5/D6). DIP switches: only set from
env `SMB2_PC_DIP` (`pc_launcher.c:203`) or the debug menu; no other writer (`grep dip_switches |=`): D13.
DIP_PLAY_STG_ALL/DIP_DEBUG additionally unlock everything and must stay 0.

### 7. Pause on focus loss, soft reset, update UI, first-run dialog
- Focus loss: no pause logic (`platform_sdl2.c:164-169` handles only QUIT and SIZE_CHANGED). Keyboard state is read
  via `SDL_GetKeyboardState` regardless of focus. Good for lockstep.
- Soft reset: `g_read_inputs_and_maybe_reset_console` and `set_console_reset_callback` are stubs
  (`stubs_gen.c:73,266`); B+X+Start does nothing. The game's `lbl_80198BA8` reset-combo flag is computed
  (`input.c:~190`) but unused on PC.
- Update UI: `pc_update_poll`/release-notes box opened at title/Mode Select "safe moment" from a background thread
  result (`video_shim.c:365-372`, `pc_quit.c:229-243`): local modal -> D11/D12.
- First-run disc dialog and extraction happen before `_prolog` (`main.c:~300`): not in the frame sequence.
- Quit: `platform_should_close()` -> `pc_quit_request` waits for card jobs (up to 30 s), exits (`pc_quit.c:90-118`);
  in a session, treat as disconnect (E9).
- Frames-affecting side effect: `s_hfr_skip` only skips HFR frames.

### 8. Uninitialised memory / heap / x64 vs i686
- Arena: 24 MiB zeroed once (`gc_mem.c` memset), mapped at 0x80000000 (x64 refuses otherwise; i686 falls back to a
  relocated block with a warning, which would shift every heap pointer: make that fatal in session). ARAM `calloc`.
  Exe `.data/.bss` are static, zero-initialised, initial values identical per build.
- Heap allocator is first-fit, deterministic given the alloc/free sequence (`os_shim.c:268-359`); `SMB2_HEAP_CHECK`
  changes sizes (D13). Freed blocks keep stale bytes: if decomp code reads uninitialised memory the value depends on
  history only, which is identical on same-arch peers; cross-arch the history of sizes differs (x64 structs larger),
  so "stale bytes" could differ in position. Cannot be settled statically (T5).
- Pointer values used as data: `qsort` callers (`boat_0.c:917`, `boat_2.c:552`, `race2.c:1784,1844,1888`,
  `race2_2.c:432`) sort player/ball records (detmath heapsort replicates ties). No evidence of pointer-keyed sorts or
  hashes, but I did not audit every compare function (only the callers). Heap addresses differ between x64 and
  i686 builds (sizes), so any pointer compare would drift cross-arch only.
- Differences x64 vs i686: struct sizes (`x64.md` table), `DPTR` fields, `PC_PTR_SCALE` buffers, HeapCell header 16 vs
  24 (user pointer always +32, `os_shim.c:256-258`), out-of-range float casts (`detmath.md`), math is bit-identical
  by construction (fdlibm + SSE2 + `-ffp-contract=off`, GC-table trig). `x64.md` reports x64 and i686 runs differ only
  where two i686 runs differ (the `OSGetTick`/`OSGetTime` cases above) => evidence the cross-arch gap is currently
  dominated by D1-D3. Cross-arch test T6.

## 4. Where the pad data goes today (call graph)
`SDL` -> `input_poll_gc_pads` (`input_sdl2.c:742`): shift `status[1]=status[0]` (L747-750) -> `SDL_GameControllerUpdate`
(L754) -> `read_port` per connected pad + `err` (L756-762) -> keyboard OR on port 1 (L766-826) -> script injection
(L828-944; `game_process_sticks` at L907 = the PC stand-in for the DOL's `g_read_inputs_and_maybe_reset_console`
0x80009A10, which `stubs_gen.c:73` stubs; it copies raw pads into `lbl_80145210` (the DOL's 0x80145210 raw-pad
array, `input_sdl2.c:698`) then runs the gate) -> derive `[2]` pressed, `[3]` released, `[4]` repeat (L945-961) ->
`pc_button_prompts_update` (L967). The game then reads `pad_status_groups`: `process_inputs` (`main_loop.c:269`,
decomp `input.c:16`: `threshold_analog_inputs`, `g_calc_frames_since_last_input_change`, `merge_inputs`) and directly
(`pad_status_groups[...].unk0[n]`). Menus merge all connected pads (`input.c:~173 use_all_pads`), in-game uses
`player_pad_map[]` (`input_sdl2.c:36`). Note the pad sampled at the end of tick N is consumed in tick N+1 (inherent
one-tick latency; the lockstep delay is added on top).

## 5. Recommended pad hook point
Hook: **inside `input_poll_gc_pads`, `pc/src/input/input_sdl2.c`, immediately before the "Derive the
pressed/released/repeat slots" loop (L945)**, active only when (a) a netplay session is running and (b) the call
comes from `video_finish_frame` (`video_shim.c:337`). Add a parameter or a second entry point
(`input_poll_gc_pads_game()` for L337, existing `input_poll_gc_pads()` stays local-only for the four modal screens).
Why here:
1. Everything the game reads (`pad_status_groups`, `lbl_80145210`, derived `[2..4]`) is produced after this point, from
   `status[0]`/`status[1]`, so overriding `status[0]` for all 4 ports here is exact; `[1]` stays correct because the
   shift at L747 copies the previous *wire* values.
2. It is the single place that is called exactly once per game-loop iteration (plus Baseball's loop and its trailing
   calls: D18), independent of render fps.
3. Sticks are already post-gate (`game_process_sticks` L907), keyboard and scripts already merged: the sampled value
   is the final value the local game would have used.
Required refactor before wiring (E3/E6):
- Sample the local device(s) into a private `PADStatus local[1]` (keyboard + any pad, aggregated; remove the
  dependence on previous `status[0]` in the keyboard/trigger code, L795-805) because after the override `status[0]`
  holds remote data.
- Wire format per port: button u16, stickX/Y, substickX/Y s8, triggerL/R u8, err s8 (+ analogA/analogB are only read
  by `test_mode.c:1275`, so can be omitted; keep them 0). Host-assigned seat -> port mapping; unseated ports get
  err=-1, all-zero.
- Also write `lbl_80145210[i].status[0]` from the bundle (D5) so Options controller screens are deterministic.
- Blocking: wait for the bundle with a loop that pumps SDL events, keeps presenting (so the window does not hang) and
  does `g_shim_frame_pulse++` (D14). HFR sub-frames of the *current* tick are drawn after this call in
  `video_finish_frame` (L398-401): a long wait delays them. If that is visible, split the hook: send the local sample
  at L337 and do the blocking receive/override just before the pacer wait (L403) -- legal because the game only
  consumes pads at the next loop top. Both variants give the same game behaviour.
- Alternative hook (rejected): overriding in decomp `process_inputs`/`g_read_inputs_and_maybe_reset_console`: it is a
  decomp file shared with the GC build, and it misses Baseball's extra video_finish_frame calls.

## 6. Recommended checksum scheme and cost
- Cannot use: whole arena or `.data/.bss` across archs (D15). 
- Primary (cross-arch, every 60 sim ticks, send u32/u64): a function `pc_state_hash()` compiled in a game TU
  (so struct field access is layout independent), feeding a 64-bit hash (xxh3/wyhash; FNV-1a is ~10x slower)
  with explicit little-endian bit patterns of non-pointer fields only. Contents, in this order:
  - tick counter, `main_mode`, `sub_mode`, `frame_counter`, `g_some_frame_counter` (`.frameCounter/.timer/.flags`),
    `modeCtrl` (non-pointer fields), `locale`.
  - RNG: `pc_libc.c` `s_rand_next` (add accessor), boat `lbl_14_data_1340`.
  - `balls[0..3]` (position, previous position, velocity, rotation, state/timers/score fields, `playerId`) and
    `current_ball` index; `world_infos`, stage animation time; `unlock_info`; `storymode_save_files[0..0xF98)`.
  - Pad state: `pad_status_groups[4].status[0..4]` (also catches hook bugs), `merged_*`, `player_pad_map[0..3]`.
  - Per-mode block selected by `modeCtrl.gameType`/`main_mode`: race2/boat/dogfight/baseball/golf/target/bowling
    player arrays (the decomp names: `BoatPlayer`, `lbl_10_bss_2D68` ... pick the position/velocity/score/state fields).
  Cost: a few KB, estimated 1-5 us per call, nothing to optimise; could run every tick into a 600-entry ring.
- Bisecting after a mismatch: keep the last 600 per-tick 64-bit hashes per client; on DESYNC exchange them to find
  the first differing tick, then exchange the per-region sub-hashes (each of the groups above hashed separately,
  ~16 regions x 8 bytes) to name the diverging region.
- Same-arch deep check (dev/CI, `--det-checksum-arena`): rolling arena hash, chunk `tick%60` of the 24 MiB (`gc_mem`
  base `0x80000000`, size `GC_MEM_SIZE`), 400 KiB per tick, about 40 us at ~10 GB/s; a full pass per second. Plus
  `.data/.bss` between linker symbols (mingw: `__data_start__`/`__bss_end__`, not verified here) when the build is the
  same on both peers. Do a full 24 MiB hash only offline (about 2-3 ms; do not do it on the game thread every tick).
- Include in handshake (not per tick): protocol version, build id, session config hash (locale, epoch, session card
  template id, seat roster), disc manifest hash (D17).
- Hash point: end of `video_finish_frame`, just before the pad exchange, so the hashed state is "after tick N".
