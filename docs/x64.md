# 64-bit (x86_64) Windows build

**Current state (2026-11-11): strategy A′ adopted.** The x64 game build uses
clang from llvm-mingw, and disc-layout structs carry `__ptr32` pointer fields
(`DPTR`). Every test mode runs on x64 with GL and D3D12 and matches the 32-bit
build apart from known nondeterminism (see "Status" below). The checklist for
x64-safe changes and the original change inventory are in
[x64_work_packages.md](x64_work_packages.md).

- Section 0 (just below) describes the build as it is now and the outcome of
  the A′ spike.
- Sections 1–6 are the original investigation and PoC (2026-11-10), kept for
  reference. The plan in 2C/3 (load-time converters) is **superseded** by A′.
  The inventory in section 1 is still the checklist.

## 0. Adopted design: A′ (clang `__ptr32` fields + low-4 GiB memory)

### Spike outcome (go)

The spike used llvm-mingw 20241217 (clang 19.1.6, UCRT), unpacked next to the
checkouts (`toolchains/`, no sudo). It took about half a day.

**What worked:**

| Check | Result |
|---|---|
| Whole-project compile | All 275 TUs (game, shims, GL + D3D12 renderers, SDL2 static libs built by GCC) compile and link with clang. Needed `-fgnu89-inline` for one TU, plus downgrades for clang-16's new default errors. |
| `T * __ptr32 __uptr` | 4 bytes, 4-aligned, zero-extended on load. Converts implicitly to and from normal pointers, so field reads, writes, `->`, `[]`, `++` and comparisons are all unchanged. |
| StageDef family, 73 fields | 25 compile errors, all of one kind: a local `T **` walking a DPTR array (`modelRefs`, `gridCellTris`) or an inline helper taking `&field`. Fixed by spelling the local `T * DPTR *`. |
| NL structs | 4 such errors. |
| GMA / TPL / ape tables / Mta / replays | Compiled unchanged. |
| Runtime | Got past every crash the GCC PoC hit (GMA entry stride, `load_nlobj`, `load_stagedef`) **with no converter code at all**. The intro (frames 100–700) is byte-identical to the 32-bit GL build. D3D12 x64 differs from GL x64 only as much as D3D12 32-bit does. The attract demo runs about 9 s into gameplay and renders identically (see "Status" below). |

**Gotchas found:**
- **mingw-w64's `_mingw.h` does `#define __ptr32`** (empty, for GCC), which silently
  turns DPTR into a plain 8-byte pointer. Fix: `pc_port/include/pc_ptr32.h` is
  force-included first in every x64 TU and `#undef`s it.
- **LLVM 19 crashed in instruction selection** ("Cannot select ... bitcast") on a
  DPTR load through a DPTR base inside `?:` (avdisp_shim.c trace print). Worked
  around with a local. It is a loud compile-time failure, not a miscompile. If
  it recurs, try a newer llvm-mingw.
- **The only true pointer-to-pointer issue** is `T **local = s->dptrArray`. Clang
  reports it as an error ("changes address space of nested pointer"), so it can't
  slip through silently.

**Why A′ instead of C:**
- A′ needs no load-time converters, which were 7–10 days in plan C.
- The memcard and `.rec` replay layouts are kept automatically, so the planned
  replay serializer isn't needed.
- No 75-site `GMA_TEXOBJS()` churn; that commit was reverted.
- No 16-byte GMA entry tables.
- Decomp changes are mostly a `DPTR` token in struct declarations, which expands
  to nothing on GC.

**Costs:**
- The x64 build needs llvm-mingw. GCC x64 is rejected with `#error` / `FATAL_ERROR`.
- It depends on all game memory being below 4 GiB, which was already accepted.

### How the x64 build works

**Build:**
```
# once: unpack llvm-mingw-20241217-ucrt-ubuntu-20.04-x86_64.tar.xz (GitHub mstorsjo/llvm-mingw)
cmake -G Ninja -S pc_port -B build64 -DCMAKE_TOOLCHAIN_FILE=$PWD/pc_port/cmake/llvm-mingw64.cmake \
      -DLLVM_MINGW_ROOT=$PWD/toolchains/llvm-mingw-20241217-ucrt-ubuntu-20.04-x86_64 \
      -DSMB2_DECOMP_DIR=$PWD/decomp -DSMB2_GAME=ON
ninja -C build64
```
The 32-bit build is unchanged: GCC with `cmake/mingw32.cmake`.

**Memory:**
- The exe is linked at a fixed image base of 0x10000000, with no dynamicbase and
  no high-entropy VA. Code and statics are below 2 GiB.
- GC RAM is reserved at 0x80000000 by a constructor in gc_mem.c, before
  SDL/GL/D3D load. The x64 build exits if the range can't be mapped.
- `pc_check_address_space()` prints where the image, stack, malloc and GC RAM
  landed, and exits if the image or GC RAM is above 4 GiB.
- The CRT heap is also low in practice (≈0x5…), but nothing guarantees that.
  **Never store a malloc'd host pointer in a DPTR field.**

**Types in `decomp/include/types.h`** (all are identical to before on GC, which
stays 21/21 OK):

| Type / macro | GC and 32-bit | x64 | Use for |
|---|---|---|---|
| `DPTR` | empty | `__ptr32 __uptr` | Pointer fields of structs whose 32-bit layout must hold: disc/file images, static word tables, and structs allocated or cleared with literal sizes **if** all their pointees live in GC RAM or the exe. Write `T * DPTR f;` and `T * DPTR * DPTR f;`. For a local that walks a DPTR array: `T * DPTR *p`. |
| `uptr` / `sptr` | `unsigned int` / `int` | 64-bit | Integer fields and globals that hold pointers. Most important: `sptr` for **signed** ones, because GC RAM addresses are ≥ 0x80000000 and an s32 round trip sign-extends them to 0xFFFFFFFF8xxxxxxx. |
| `PC_PTR_SCALE` | 1 | 2 | Raw `u8 buf[N]` buffers that hold arrays of pointer-bearing structs. |
| `PC_A32(x)` (`pc_addr32.h`) plus generated fixups (`tools/gen_addr32_fixups.py`) | — | — | Address words inside u32 data tables. |

**DPTR is in place for:**
- all `Stage*` structs (stage.h)
- NlObj, NlObj_UnkChild, NlMesh.texObj, NlModelHeader
- GMA, GMAModelEntry, GMAModel.texObjs, the GMA TEV layer copies, TPL
- ApePartEntry/List, ApeModelTable/Entry, ApeData, ApeClipInfo, ApeClipGroup
- Mta
- Replay* in recplay.c and cmp_recplay.c
- the PC mirrors PcGMA, PcGMAEntry, PcTPL

**Other fixes already in:**
- `Ape.unk0`/`unk14` are `sptr`.
- The main_loop.c u32 globals that other TUs declare as pointers are `uptr`.
- Heap handles are `sptr`.
- The Thread pool and ord-table buffers use `PC_PTR_SCALE`.
- Static tables: ape_data and data_init_gen via `PC_A32`; author_preload via `uptr`.

**Debugging:**
- The x64 crash handler prints full 64-bit registers.
- `-gline-tables-only` is on, so this symbolizes a crash dump:
  ```
  (grep -o 'rip=[0-9A-F]*' log | sed s/rip=/0x/; grep -o 'stack\[[0-9]*\] 10[0-9A-F]\{6\}' log | awk '{print "0x"$2}') \
    | $LLVM_MINGW_ROOT/bin/llvm-symbolizer --obj=build64/bin/smb2_pc_port.exe
  ```
  The stack-scan frames are heuristic.
- Inventory: `-DSMB2_PTR_WARNINGS=ON` (clang, x64) reports 268 pointer↔int cast
  warnings. Grep the build log for `-Wpointer-to-int-cast`, `-Wint-to-pointer-cast`,
  `-Wvoid-pointer-to-int-cast` and `-Wint-to-void-pointer-cast`.

**Bring-up tools:**
- `SMB2_HEAP_CHECK=1` (heap guards with allocation sites)
- `tools/x64test/structsizes.py` (struct sizes, 32-bit vs x64)
- `tools/x64test/crossdecl.py` (definition vs declaration type mismatches)

All are described in x64_work_packages.md.

**Test harness:** `pc_port/tools/x64test/modes.sh` runs the same input script on any
build and renderer, then diffs the frame dumps and writes comparison sheets.
See its header and x64_work_packages.md.

## 1. What bakes in 32-bit pointers

The decomp has 251 `.c` files and about 271k lines; the port builds 270 TUs. The first
plain x64 build failed in only **8 TUs**, with 6,425 errors. Of those, 6,400 were
`initializer element is not constant` from 4 data tables. Nearly everything else
*compiles*. The real problems are silent: layout mismatches and truncations that
only show up at runtime. They fall into the groups below.

### 1a. Disc data used in place, with offsets relocated into pointer fields

There are **46 struct types**, about **146 declared pointer members** (about 186
pointer slots per image when counting embedded `StageKeyframeChannel.frames`), and
about **2,100 dereference sites** (grep-estimated). The deref sites only need changing
under strategy A.

| Format | Structs (header) | Ptr fields | Relocated by | Deref sites (approx.) |
|---|---|---|---|---|
| Stagedef `.lz` | StageDef + 17 children (stage.h:39-380) | 73 | stage_load.c:290-498 (`OFFSET_TO_PTR`) | ~930 (+~290 ambiguous) |
| NL models `.lz` | NlObj, NlObj_UnkChild(_Child), NlMesh, NlModelHeader (nl2ngc.h:74-113, stage.c:132) | 8 | nl2ngc.c:232-270 | ~66 |
| GMA | GMA, GMAModelEntry, GMAModel.texObjs, GMATevLayer, ApeModelTable/Entry | 14 | endian_gma.c (`g_init_gma`), avdisp_shim.c | ~566 (`modelEntries` alone: 449) |
| TPL | TPL header (bitmap.h:20) | 3 | bitmap.c:240-253, endian_gma.c | ~48 |
| ape `.mta/.ska/.skl` | Mta (skeleton.h:73) | 2 | skeleton.c:894-911 (`p[i] += (u32)archive`) | ~16 |
| Scene `scndat_*.bin` | Scene, SceneObj, SceneAnim (scnplay.c:24-44) | 9 | scnplay.c:1158-1173 | ~66 |
| Dialog `dlg/*.bin` | DialogTbl, DialogData (dialog.c:17-40) | 3 | dialog.c:1549-1556 | ~11 |

| Embedded ape tables | ApePartEntry, ApePartList (ape_internal.h:135-150) | 3 | static data, ape.c:128 | ~9 |

Things in this group that are not obvious:
- **Every relocator adds the base through `(u32)`.** That truncates on x64 even if
  the layout were right. Fixed in the PoC for `OFFSET_TO_PTR` (now `uptr`).
- **The file's `GMAModelEntry` table is 8 bytes per entry; native x64 needs 16.** It
  breaks all 449 `modelEntries[i]` sites. Fixed in the PoC: a native table is built.
- **Six pointers are runtime-only but sit inside layout-fixed images**, so the file
  bytes around them must not move:
  - `GMAModel.texObjs` @0x24 (on x64 it would land on 0x28 and overwrite the GCMF data)
  - `GMATevLayer.texObj` @0x08 and `.imageData` @0x14
  - `NlMesh.texObj` (display lists start at +0x50)
  - `NlModelHeader` `ptr[-2]` / `ptr[-1]`
  - `NlObj_UnkChild_Child.unk0` (a u32 relocated as a pointer)
- **Loops step through disc arrays by sizeof(struct)**, e.g. `coll++`, `bg++`,
  `scene++`, `entry++`, `igTrack++` (46+ sites). They are fine as long as the array has
  native layout.
- **Formats that are already x64-safe:** the MusyX sound banks (musyx_shim.c parses
  them into its own structs) and the ApeMal clip catalogs (offsets stay u32 and are
  converted at the use site). TPL texel data and `imageOffset` are offsets too.

### 1c. Pointer↔integer casts

**About 1,900 `(u32)`/`(s32)` casts appear in decomp/src, but most are numeric.**
Compiler-verified, x86_64 `-Wpointer-to-int-cast -Wint-to-pointer-cast` over all 270
TUs gives:

- **Before the PoC:** 1,270 unique diagnostics. 997 were in the `.inc` tables; the
  remaining 273 (129 p2i, 144 i2p) were on **234 distinct lines**.
- **After the PoC:** 260 diagnostics on **227 lines**, 8 of them in pc_port.

Classification:

**Not visible to the compiler:**
- **12 globals are defined `u32` in one TU and declared as a pointer in others.** Most
  are in main_loop.c:458-470, e.g. `g_stage_nl_buf`, `g_some_tpl_buffer`, `lbl_1_bss_1320`.
  On x64 an 8-byte access then lands on a 4-byte object.
- **Heap handles are `int` (alloc.c:94-97) but `extern void *` in about 39
  declarations.** os_shim.c pads `currentHeap` to 8 bytes as a workaround.

**Implicit declarations:** 373 warnings covering 183 functions. Only 1 of them truncates
a pointer: bowling_5.c:108 `GXGetTexObjData`.

### 1d. The PC shim layer itself

- **gc_mem / os_shim keep the arena and heap API in u32.** Examples: `OSGetArenaLo`,
  `OSCreateHeap(u32,u32)`, `struct Heap {u32 start,end}`, `gc_arena_*_initial`. This
  works below 4 GiB.
- **ar_shim.c writes structs that outgrow their decomp storage.** `ShimARCHandle`
  (four pointers, 0x1C → 0x38 bytes) and `ShimARCFileInfo` go into blobs that are
  `u8[0x1C]` / `u8[0xC]` in ape.c:30-38. That overflows a static and a stack object.
- **endian_gma.c declared `struct PcFile { u8 raw[0x50]; }` for `struct File`.** On x64
  `struct File` is bigger because DVDFileInfo holds pointers, so the stack was smashed.
  Fixed in the PoC. **The same pattern needs auditing in every shim that mirrors a
  decomp struct as bytes.**
- **endian_fix.c's stagedef walker and `pc_swap_replay` use u32 offsets and the
  32-bit field offsets.**
- **Crash dumps printed 32-bit registers.** Fixed in the PoC: `%p` and the full x64
  register set.
- **The renderer is clean.** Handles go through `uintptr_t`. However, the PC `GXTexObj`
  in render.h is **exactly 32 bytes on x64**, which leaves no headroom against
  `u32 dummy[8]`. The D3D12 work must not grow it.

### 1e. Other categories

- **Absolute GC addresses `*(u32*)0x800000F8` (11 sites).** These work only while GC
  RAM is mapped at exactly 0x80000000.
- **Serialization:** the memcard replay writes the raw `struct Replay`, which has 38
  pointer fields converted to offsets (cmp_recplay.c:1004-1025, memcard_mkb2.c). Its
  layout differs on x64, so x64 saves are incompatible with 32-bit-PC and GC saves
  unless the serializer writes the 32-bit layout explicitly.
- **None found:** unions of a pointer with a u32, packed structs with pointers, `va_arg`,
  or static asserts in the decomp. `%x` of a pointer appears only in debug prints.
- **The REL stack walkers** (`(u32)sp != 0xFFFFFFFF`) are harmless because
  `OSGetStackPointer` returns NULL on PC.

## 2. Strategies (original analysis; A′ was adopted, see section 0)

### A. Low-4 GiB, with every disc pointer field as a 32-bit slot (GCC)

All game memory stays below 4 GiB. All ~146 disc pointer members become `PTR32(T)`
(u32 storage), and every dereference goes through `P32_GET`/`P32_SET`.

- **Pros:**
  - The file layouts and the decomp's own relocation code stay as they are.
  - No converters.
  - Most u32 casts become safe as-is.
- **Cons:**
  - About **2,100 deref sites** (930+ for the stagedef alone) get rewritten with macros
    across the decomp. That churn is permanent and future decomp work has to follow it.
  - The type safety of the field accesses is lost.
  - It still needs every fix in 1b/1d, plus a fix for the s32 sites.
- **Effort:** about 3-4 weeks. The edits are mechanical but huge and hard to review.
  **Risk:** medium.

### A′. Same as A, but with clang `T * __ptr32 __uptr` fields

Clang and MSVC have true 32-bit pointer types. Only the ~146 field *declarations*
change; deref sites compile unchanged.

- **Needs a toolchain switch** to llvm-mingw (not installed here) or clang-cl.
- **Unverified:** whether clang's mingw target accepts `__ptr32` (it is an MS
  extension, enabled by `-fms-extensions`), and how it interacts with the GCC-built
  SDL/static libs.
- **Still needs** the static-table fixups and everything in 1b/1d.
- **Effort:** a 1-day spike to validate; if it works, about 1.5-2 weeks overall.
- **Risk:** toolchain risk, and every future build depends on clang.

### B. Fully native 64-bit (portable)

Translate every format into native structs at load time, convert every
pointer-in-integer field to `uptr` or a real pointer type, and drop the low-memory
assumption completely. This is the only option that works where the low 4 GiB is
unavailable. On **macOS arm64** the whole low 4 GiB is `__PAGEZERO`, and on Linux it
works only via `MAP_32BIT` and friends.

- **Effort:** about 5-7 weeks. It covers all of C below, plus ~230 cast lines, the 6
  layout-fixed runtime pointers (handle table or full GCMF re-layout), the heap/arena
  API and ARAM in the shims, and 12 cross-TU declarations.
- **Risk:** medium-high. There is a long tail of silent truncation.

### C. Hybrid (recommended)

1. **Low-memory safety net.**
   - The exe is linked at a fixed image base of 0x10000000, without dynamicbase or
     high-entropy ASLR.
   - GC RAM is reserved at process start at a fixed low address.
   - All game heaps and loaded files live in it, so u32-stored pointers round-trip
     unchanged.
   - Verified in the PoC: the image, stack, CRT malloc and GC RAM all report < 4 GiB.
   - **Proposed change:** on x64, move GC RAM below 2 GiB (e.g. 0x40000000), so s32/int
     storage round-trips too. Then route the 11 absolute `0x800000xx` reads through
     `gc_mem_ptr()` under `#ifndef __MWERKS__`. The alternative is to keep 0x80000000
     and fix the ~25 s32 sites plus the `APE_DATA` macro.
2. **Native layout for formats whose pointers are relocated offsets.**
   - Covers the stagedef family (and the embedded baseball stagedefs), the NL object
     tables, the Mta archive tables, scene, dialog, .rec/memcard replays and the GMA
     entry table.
   - **A load-time converter in pc_port**, run where the endian swap runs today, widens
     the 32-bit image into the native layout in a heap copy.
   - **Where possible it keeps the values as offsets,** so the decomp's own relocation
     code (`OFFSET_TO_PTR`, now `uptr`) still runs unchanged.
   - endian_fix.c's `sd_traverse` already visits every stagedef pointer field. It
     becomes "swap + widen" driven by a small per-struct field table: u32 / u16 /
     f32 / ptr→type / count.
   - **Deref sites do not change.**
3. **`PTR32` slots only for runtime pointers inside layout-fixed images.** These are
   GCMF `texObjs`, the TEV layer `texObj`/`imageData`, `NlMesh.texObj`, the
   NlModelHeader words and `NlObj_UnkChild_Child.unk0`. That is about 100-150 sites
   behind macros that expand to the plain field on GC. Done in the PoC for GMA: 75
   texObjs sites plus 10 TEV-layer sites.
4. **Static tables.**
   - Address words use `PC_A32()` plus generated startup fixups. Done for ape_data (651)
     and data_init_gen (75).
   - Pointer-bearing records (ApePartEntry) are converted to native at init. Done.
   - `void*`-of-packed-words tables (how_to, name_entry2, ape_face_data) become u32
     tables, or are regenerated typed, on PC.
5. **Fix the layout-size bugs.** These are needed whatever the strategy: the 30
   memsets, 8+ allocations, ~6 hard offsets, the ARC handle overflow, 12 cross-TU
   declarations, heap handle types, the shim byte-blob mirrors, the replay serializer
   and bowling_5.c:108.
6. **Later and optional:** retire the safety net by turning the remaining ~110 u32
   pointer stores into `uptr`. Add a debug mode that maps GC RAM above 4 GiB and keeps
   the image ASLR'd high, to flush out truncations. That is what a macOS or Linux arm64
   port would need.

**Why C:**
- The ~2,100 deref sites stay untouched, unlike A.
- No toolchain change, unlike A′.
- It needs weeks less than B, while every step still moves towards B.
- Layout conversion is concentrated in about 10 converters that the PC layer already
  owns, since the swap code is there. Decomp churn stays small and always under
  `#ifndef __MWERKS__`, or uses macros that are identical on GC.

**Total effort: about 3-4 weeks.** **Risk: medium.** The unknown is the long tail of
in-place writes into disc data and struct-size assumptions that only fail at runtime.

## 5. Risks

- **Silent truncation and layout bugs fail at runtime, often far from the cause.** They
  need mode-by-mode testing; there is no compile-time completeness check for in-place
  disc data.
- **Widened copies cost memory.** If they come out of GC-sized heaps (stage heap etc.),
  the heaps may need to grow on x64. Some code may assume exact heap sizes.
- **A third-party DLL could take the GC RAM range before our constructor runs.** That
  has not been observed. Mitigations: map it from a TLS callback, or from the earliest
  possible point.
- **Replay and memcard compatibility** depend on the serializer decision (§6).
- **The concurrent D3D12 branch** must keep `GXTexObj` at ≤32 bytes and keep host
  pointers out of u32 game fields.

## 6. Decisions (answered 2026-11-11)

Answers: Windows x64 only for now (keep phase-5 portability possible); A′ spike first, and it was adopted; keep GC RAM at 0x80000000 and fix s32 pointer stores; keep memcard/replay saves compatible (automatic with DPTR); baseball must be converted before the work is finished.

Original questions:

1. **Is "Windows x64 with a low-4 GiB safety net" acceptable, or is portability a
   goal** (macOS arm64 or Linux)? That decides whether phase 5 is required, and leans
   C→B.
2. **On x64, should GC RAM move below 2 GiB** (patching 11 absolute-address sites), or

5. **Should baseball stay disabled on x64** until its embedded stagedefs are converted
   (phase 2, last)?
